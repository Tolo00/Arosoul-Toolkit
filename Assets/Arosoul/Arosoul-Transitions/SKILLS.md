# SKILLS.md: Arosoul Transitions

Guide for AI agents working with, extending, or writing code against `com.arosoul.transitions`.

- **Package version:** 1.0.0
- **Unity version:** 6000.6 (Unity 6.6)
- **Language/UI:** C#, UI Toolkit for the runtime overlay and editor tooling. Do not introduce uGUI into this package.
- **Assemblies/namespaces:** runtime `Arosoul.Transitions`; editor `Arosoul.Transitions.Editor`.
- **Generated API:** `TransitionIds` in the **global namespace** (no `using` needed; `using Arosoul.Transitions;` is still needed for `TransitionAPI`, `TransitionId` and the other runtime types).
- **Editor automation:** `Arosoul.Transitions.Editor.TransitionsAgentTools` creates, inspects, validates and regenerates transitions from code (see section 6.1).
- **Dependency direction:** this package works independently. `com.arosoul.scenes` depends on it; Transitions must not depend on Scenes.

---

## 1. Mental model and architecture

- **`TransitionDefinition`** is a `ScriptableObject` asset. It stores default timings and visual settings, builds a UI Toolkit visual tree, and applies its visual state during playback.
- **`TransitionId`** is a serializable, type-safe integer reference to a definition. Use the generated `TransitionIds` members in code or the inspector drawer; do not use asset names, strings, or list indices as runtime identifiers.
- **`TransitionRegistry`** is generated by the editor. It contains every transition definition found in the project and is added to Player Settings' preloaded assets so it can be found in a player build.
- **`TransitionManager`** owns one runtime UI Toolkit overlay and runs at most one transition at a time. It is created lazily through `TransitionAPI.Play` and persists across scene loads.
- **`TransitionHandle`** is the per-playback control/status object. It exposes phase changes, progress, release, cancellation, and awaitable waits.
- **`InputBlocker`** is a separate, reference-counted static service. A transition optionally acquires one block for its lifetime.

Runtime flow:

```text
TransitionAPI.Play
    -> lazy TransitionManager
    -> TransitionRegistry lookup by TransitionId
    -> TransitionDefinition.Build
    -> In -> Hold -> Out
    -> TransitionHandle reaches Completed or Cancelled
```

There is no transition queue. A new play request either starts, interrupts the active transition, or is rejected based on priority.

## 2. Files, generated assets, and setup

| What | Location |
|---|---|
| Registry asset | `Assets/Generated/Transitions/TransitionRegistry.asset` |
| Generated constants | `Assets/Generated/Transitions/TransitionIds.cs` |
| Default definition asset folder | `Assets/Generated/Transitions/Definitions/` |
| Runtime implementation | `Runtime/Core/`, `Runtime/DefaultTransitions/`, `Runtime/Shared/` |
| Editor implementation | `Editor/`, including `Editor/Generation/` |

Editor menu items:

- **Tools > Arosoul > Transitions > Transitions**: create, inspect, preview, and delete definitions.
- **Tools > Arosoul > Transitions > Regenerate Ids**: force a registry and generated-id refresh.

The editor refreshes ids and the registry when a definition asset is created, changed, moved, or deleted, and before a build. The generated registry is also added to Player Settings' preloaded assets. Do not remove that preloaded asset entry unless you have replaced the registry-loading mechanism.

**Never hand-edit `Assets/Generated/Transitions` or generated `TransitionIds.cs`.** The registry and source file are overwritten by the editor tooling.

The generated source has no assembly definition and therefore compiles into `Assembly-CSharp` by default. Code inside a project `.asmdef` cannot reference types compiled into `Assembly-CSharp`. If an `.asmdef` assembly needs `TransitionIds`, put an appropriate `.asmdef` beside the generated source (referencing `Arosoul.Transitions`) and reference that generated assembly from the game assembly. Account for any existing parent/nested assembly-definition layout before adding one.

The editor creates the built-in Fade, Slide, and Loading Screen assets on first initialization **only if it finds no `TransitionDefinition` assets at that time**. If the project already contains a custom definition, do not assume those defaults will also be generated.

## 3. Playing and controlling transitions

```csharp
using Arosoul.Transitions;

TransitionHandle handle = TransitionAPI.Play(TransitionIds.Fade);
```

`TransitionAPI` exposes:

- `Play(TransitionId)` and `Play(TransitionParameters)`.
- `IsPlaying` and `GetActive()`.

`IsPlaying` and `GetActive()` do not create the manager. `Play` creates it on first use. The manager/overlay persists across scene loads.

### Parameters

`TransitionParameters` is an immutable value. Use its `With...` methods to make modified copies.

```csharp
TransitionParameters.Default(TransitionIds.Fade);            // Definition defaults, if registered
TransitionParameters.Symmetric(TransitionIds.Fade, 0.4f, 0.2f);

var parameters = TransitionParameters.Default(TransitionIds.Fade)
    .WithTimes(inTime: 0.3f, minHoldTime: 0.2f, outTime: 0.5f)
    .WithPriority(10)
    .WithHoldUntilReleased();
```

Properties: `Id`, `InTime`, `MinHoldTime`, `OutTime`, `Priority`, `HoldUntilReleased`.

- `Default(id)` reads the timings from the registered definition. If it cannot find one, it returns fallback timings (`0.5 / 0.2 / 0.5`); playback still fails if the id is not in the runtime registry.
- A `TransitionId` implicitly converts to `TransitionParameters` using `Default(id)`.
- `HoldUntilReleased` makes the handle wait for both the minimum hold time and an explicit `Release()` before entering Out. Without it, the handle starts released and only the minimum hold time applies.

### Handle and phase lifecycle

Phases are ordered: `Pending`, `In`, `Hold`, `Out`, `Completed`, `Cancelled`.

```csharp
var handle = TransitionAPI.Play(
    TransitionParameters.Default(TransitionIds.LoadingScreen)
        .WithHoldUntilReleased());

await handle.WaitForPhaseAsync(TransitionPhase.Hold);
handle.SetProgress(0.5f, "Loading");
// Perform the work hidden behind the transition.
handle.Release();
await handle.WaitUntilFinishedAsync();
```

`TransitionHandle` exposes `Phase`, `Progress`, `Message`, `IsFinished`, `IsReleased`, `Parameters`, `PhaseChanged`, `Release()`, `SetProgress(float, string)`, `Cancel()`, `WaitForPhaseAsync(phase)`, and `WaitUntilFinishedAsync()`.

Important semantics:

- `SetProgress` clamps progress to 0–1. A transition must override `OnProgress` to display it; the default definitions do not all use progress.
- `OnProgress` is delivered while in Hold, when new progress has been reported.
- `Cancel()` removes the active transition visuals immediately and finishes the handle as `Cancelled`.
- `WaitForPhaseAsync` compares the numeric phase order. Waiting for `Hold`, `Out`, or `Completed` returns early if the handle is `Cancelled` (because `Cancelled` is ordered after `Completed`). Do not use `WaitForPhaseAsync(Cancelled)` as a general terminal-state wait: a normally completed handle will never reach that phase. Use `WaitUntilFinishedAsync()` to wait for either terminal state, then inspect `handle.Phase`.
- Unity `Awaitable` instances are single-use. Do not await the same returned `Awaitable` more than once.
- `TransitionManager.TransitionStarted` and `TransitionManager.TransitionFinished` are static events. `TransitionFinished` is raised when a started playback is finalized (including cancellation or a runtime exception). A request rejected immediately because its id is missing or its priority is insufficient returns a cancelled handle without going through the normal started/finished event pair.

### Priority and timing

- If a transition is active, a new transition starts only when its priority is **strictly greater** than the active transition's priority.
- Equal or lower priority: the new handle is immediately `Cancelled` and a warning is logged.
- Higher priority: the active transition is cancelled and the new one starts.
- Time is unscaled. Transitions continue while `Time.timeScale` is zero; the package does not set or change `Time.timeScale` itself.

## 4. Authoring a transition

1. Create a non-abstract class derived from `TransitionDefinition`.
2. Implement `Build()` and `Apply(...)`.
3. Create an asset through **Tools > Arosoul > Transitions > Transitions > New Transition**, `[CreateAssetMenu]`, or `TransitionsAgentTools.CreateDefinition<T>(assetName, key)` (after the new type has compiled).
4. Let the editor assign the id and generate `TransitionIds.<Key>`; do not assign `_id` manually.

```csharp
[CreateAssetMenu(menuName = "Arosoul/Transitions/Wipe", fileName = "Wipe")]
public sealed class WipeTransition : TransitionDefinition
{
    [SerializeField] private Color _color = Color.black;

    public override VisualElement Build()
    {
        var root = new VisualElement { name = "wipe-transition" };
        StretchToFill(root); // Optional protected helper; the manager also stretches the returned root.
        root.style.backgroundColor = _color;
        root.pickingMode = PickingMode.Ignore;
        return root;
    }

    public override void Apply(VisualElement visual, TransitionPhase phase, float t)
    {
        // Set the visual state for In, Hold, or Out.
    }
}
```

Base definition settings: `DefaultInTime`, `DefaultMinHoldTime`, `DefaultOutTime`, easing curve, `BlockInput`, key, and assigned id.

Extension contracts and rules:

- `Build()` is called for every playback. Build a fresh visual tree each time; do not cache or reuse a `VisualElement` across plays.
- Keep per-play visual state on the returned tree (for example `visual.userData`), not in mutable fields on the shared `ScriptableObject` asset.
- The manager stretches the returned root to fill the overlay. `StretchToFill` is available for children that must fill their parent.
- `Apply(visual, phase, t)` should be deterministic and idempotent. It is also called by the editor preview, so it must not depend on runtime-only state or cause gameplay side effects.
- The manager handles Hold itself. It calls `Apply(Hold, t)` over `MinHoldTime`, then calls `OnProgress` while the handle remains held. `PlayAsync` is used for In and Out only.
- The base `PlayAsync` drives `Apply` over time using `Time.unscaledDeltaTime`, `Awaitable.NextFrameAsync(cancellationToken)`, and the definition's easing curve.
- Override `PlayAsync` only when needed for a custom animation implementation. Use unscaled time, honour the cancellation token, and preserve the definition's easing behaviour if that is intended. Do not assume the editor preview executes this override: the preview drives `Apply` directly.
- Serialized definition fields must be Unity-serializable. Avoid storing a runtime `VisualElement`, a handle, or other per-play state on the asset.

Optional overrides:

- `OnProgress(VisualElement visual, float progress, string message)` for progress UI.
- `PlayAsync(VisualElement visual, TransitionPhase phase, float duration, CancellationToken cancellationToken)` for custom In/Out animation.

Built-in definitions:

- `FadeTransition`: full-screen color fade using opacity.
- `SlideTransition`: full-screen panel sliding from a configurable direction.
- `LoadingScreenTransition`: fade with progress bar, message, and optional randomly selected tip. Its progress display is driven by `SetProgress`; Scenes forwards operation progress automatically.

## 5. Input blocking

```csharp
using System;
using Arosoul.Transitions;

IDisposable block = InputBlocker.Acquire("Inventory closing");
// ... input should be considered blocked ...
block.Dispose();

bool blocked = InputBlocker.IsBlocked;
int count = InputBlocker.BlockCount;
var reasons = InputBlocker.GetReasons();
InputBlocker.BlockedChanged += OnBlockedChanged;
```

- `Acquire(reason)` returns an `IDisposable` token. Blocks are reference-counted; input remains blocked until every token has been disposed. Disposing the same token more than once is safe.
- `BlockedChanged` fires only when the overall state changes (0 to 1 active tokens, or 1 to 0), not for every count change.
- `GetReasons()` returns the reasons for currently active tokens.
- Subscriptions and active tokens are cleared at `RuntimeInitializeOnLoadMethod(SubsystemRegistration)`. Subscribe in `OnEnable` and unsubscribe in `OnDisable`; do not assume static subscriptions survive entering Play Mode.
- A transition acquires its own token only when its definition's `BlockInput` setting is enabled.
- The overlay catches UI Toolkit pointer input only through the `TransitionManager` root's picking mode. `InputBlocker.Acquire` alone does not create the overlay or intercept events. Once the overlay exists it follows `BlockedChanged`, and when it is created it starts from the current `InputBlocker.IsBlocked` state, so a block acquired before the first transition (for example by a scene operation) is honoured.
- It does not disable keyboard/gamepad navigation or gameplay actions. The project's input layer must subscribe to `BlockedChanged` or check `IsBlocked` and disable the relevant actions itself.
- Scenes operations can independently acquire an `InputBlocker` token. Their `WithInputBlocking(false)` setting does not override a transition definition's own `BlockInput` setting.

## 6. Registry, ids, and editor workflow

The **Tools > Arosoul > Transitions > Transitions** window:

- Lists definitions by key; the type name is shown separately.
- Creates instances of non-abstract `TransitionDefinition` types.
- Shows the normal inspector and a live preview.
- Deletes the selected asset after confirmation. Deletion cannot be undone through this window.
- Reports duplicate keys. Generated C# member names are sanitized and receive numeric suffixes when necessary.

Id/key rules:

- The integer id is stored on the definition asset. Existing unique positive ids are retained during refresh; missing or duplicate ids are allocated new positive ids.
- Duplicating an asset results in a new id for the duplicate during refresh.
- The key defaults to a sanitized asset name when first assigned and is editable on the asset. Renaming the key changes the generated C# member name, not the serialized integer id.
- Generated member names are sanitized to valid C# identifiers; collisions receive `_2`, `_3`, and so on.
- Do not depend on the integer id being a permanent external identifier after its asset has been deleted. Allocation is based on ids still present in the project; the allocator does not maintain a separate tombstone history.
- `TransitionId.None` is the default value (`0`). A missing/invalid id cannot be played and logs an error.

`TransitionRegistry` lookup uses the generated registry. In the Editor it can locate the asset through `AssetDatabase`; in a player it finds the registry loaded as a preloaded asset. If a custom `PanelSettings` is assigned to the registry, that asset is used by the overlay. Otherwise the manager creates default panel settings in code (1920×1080 reference resolution, scale-to-screen, default sorting order 32000); assign custom panel settings if project theme, scaling, or sorting needs to differ.

### 6.1 Editor automation API (`TransitionsAgentTools`)

`Arosoul.Transitions.Editor.TransitionsAgentTools` is a public, editor-only static API for agents, editor scripts and `-executeMethod` wrappers. Every method that changes assets refreshes ids, the registry and `TransitionIds.cs` before it returns (also while scripts are compiling; it throws `InvalidOperationException` only while playing or importing).

```csharp
using Arosoul.Transitions;
using Arosoul.Transitions.Editor;

FadeTransition fade = TransitionsAgentTools.CreateDefinition<FadeTransition>("QuickFade", key: "QuickFade");
string[] diagnostics = TransitionsAgentTools.Validate(); // fix every "ERROR:" entry, review "WARNING:" entries
string summary = TransitionsAgentTools.Describe();       // key, id, type, default times, asset path per transition
```

| Method | Use |
|---|---|
| `GetDefinitionTypeNames()` | Full names of every creatable (non-abstract) `TransitionDefinition` type. |
| `FindDefinitions()` / `FindDefinition(key)` | All definitions ordered by asset path / one by key (`null` if missing). |
| `CreateDefinition<T>(assetName, key = null)` | Create a definition asset in `Assets/Generated/Transitions/Definitions` and assign its id. Overloads take a `Type` or a type name. The asset name is made unique if taken. |
| `SetKey(definition, key)` | Change the key (the generated member name). The id is kept. |
| `DeleteDefinition(definition)` | Delete the asset and refresh. Serialized references to its id stop resolving. |
| `Regenerate()` | Assign ids, write the registry, regenerate `TransitionIds.cs`; returns its path. |
| `Validate()` | `ERROR:`/`WARNING:` diagnostics: missing/duplicate ids, member-name collisions, missing or stale registry, registry not preloaded, stale `TransitionIds.cs`. Empty means valid. |
| `Describe()` | Text summary of every definition. |

To change definition settings (times, curve, colours), edit the asset with `SerializedObject` in an editor script and save it; the generated ids are unaffected. Newly generated `TransitionIds` members are usable after the next script compilation.

## 7. Rules for agents and gotchas

- Use `TransitionId` and generated `TransitionIds` constants or serialized inspector fields. Never identify a transition by string, asset-list index, or a manually copied integer.
- Do not hand-edit `_id`, generated `TransitionIds.cs`, or the generated registry.
- Do not introduce a dependency on `Arosoul.Scenes`; Transitions is the lower-level package.
- Do not add uGUI components. Runtime and editor visual trees use UI Toolkit.
- Do not assume a transition request is accepted. Check `handle.Phase` for `Cancelled` when it matters.
- Do not assume `InputBlocker` disables the project's gameplay input. It is a signal/ref-count service; the project input layer owns action disabling.
- New static state must be reset from a `RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)` method, especially for Enter Play Mode Options with domain reload disabled.
- `LazyLoaded<T>` creates a persistent `DontDestroyOnLoad` GameObject on first access. Derived singleton types must clear their static instance in SubsystemRegistration by calling `ClearInstance()` (as `TransitionManager` does).
- If Unity reports a missing runtime theme warning, assign a suitable `PanelSettings` asset to `TransitionRegistry`.

## 8. Extending and testing

Good extension points:

- Custom transition visuals/behaviour: derive from `TransitionDefinition`.
- Custom overlay panel configuration: assign `PanelSettings` on `TransitionRegistry`.
- Shared lazy MonoBehaviour service: `LazyLoaded<T>` is available, but use it only when a persistent, on-demand component is appropriate.
- Pure generation logic: `IdentifierUtility`, `StableIdAllocator`, and `IdCodeGenerator` are separated from Unity runtime code and have Editor tests. `IdCodeGenerator.Generate` takes a `null` namespace to emit global-namespace classes (used by Transitions and Scenes).
- Editor automation: add new scripted operations to `TransitionsAgentTools` so agents keep a single entry point.

Test coverage in the package:

- `Tests/Editor`: stable id allocation/generation, `TransitionId`, `TransitionParameters`, reference-counted `InputBlocker`, and built-in transition visuals/progress.
- `Tests/PlayMode`: transition phase progression, input block lifetime, Hold-until-released, priority rejection, priority interruption, and overlay pointer blocking when the overlay is created while input is already blocked.

Run both package test assemblies (`Arosoul.Transitions.Tests.Editor`, `Arosoul.Transitions.Tests.PlayMode`) after changing runtime or editor behaviour. Play Mode tests must be run asynchronously by automation bridges because entering Play Mode reloads the domain.

## 10. Code conventions

Match the existing code when adding or modifying code:

- Allman braces, 4-space indentation, and namespace matching the assembly (`Arosoul.Transitions` or `.Editor`).
- Private fields use `_camelCase`; public types, methods, and properties use `PascalCase`.
- Use `[SerializeField] private` for serialized private fields, as the existing package code does.
- Add `/// <summary>` XML documentation to public types and members; keep other comments short and explain non-obvious behaviour.
- Keep runtime code free of `UnityEditor` references. Editor-only code belongs in `Editor/` and the editor assembly.
- Preserve the runtime/editor assembly boundary and the dependency direction between packages.
